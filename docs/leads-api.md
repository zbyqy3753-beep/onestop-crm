# API לשליחת לידים — ONE STOP CRM

מסמך החוזה שנשלח לשותפים חיצוניים. המימוש: [`src/app/api/leads/route.ts`](../src/app/api/leads/route.ts).

## כתובת

```
POST https://<host>/api/leads
```

## כותרות

| כותרת          | ערך                  |
| -------------- | -------------------- |
| `Content-Type` | `application/json`   |
| `x-api-key`    | המפתח האישי של השותף |

המפתחות מוגדרים במשתנה הסביבה `LEADS_API_KEYS` (זוגות `מפתח:שם-שותף`, מופרדים
בפסיק). בלי המשתנה הזה כל בקשה נדחית ב-401 — כולל בפיתוח מקומי.

## גוף הבקשה

```json
{
  "fullName": "שם לקוח",
  "phone": "0501234567",
  "email": "email@example.com",
  "source": "שם הספק",
  "category": "cellular"
}
```

**שדות חובה:** `fullName`, `phone`

**שדות אופציונליים:** `email`, `source`, `category`, `message`, `packageName`,
`providerName`, `price`

**ערכי `category` אפשריים:** `cellular` / `internet` / `tv` / `triple` /
`electricity` / `general` — או התווית העברית המקבילה (`סלולר`, `אינטרנט`,
`טלוויזיה`, `טריפל`, `חשמל`, `כללי`).

### איך כל שדה נוחת במערכת

| שדה בבקשה                            | איפה הוא מופיע ב-CRM                             |
| ------------------------------------ | ------------------------------------------------ |
| `fullName`                           | שם הליד                                          |
| `phone`                              | טלפון (מנורמל לספרות; `+972` מומר ל-`0`)         |
| `email`                              | אימייל                                           |
| `source`                             | עמודת "מקור". אם לא נשלח — נרשם שם השותף מהמפתח  |
| `category`                           | קטגוריית העניין (`cellular` → "סלולר")           |
| `packageName`                        | עמודת "חבילה" (גם `package` / `plan` מתקבלים)    |
| `providerName`                       | "ספק נוכחי", אם השם מזוהה. אחרת — בהערה           |
| `message`, `price`                   | ההערה הראשונה על הליד                            |

כל ליד נכנס בסטטוס **"חדש"** וכליד **חם**.

### כששדה `source` נושא פרטים אמיתיים

מערכות שלא שולחות `packageName` / `category` נוטות לדחוס את מה שיש להן
לשדה החופשי היחיד. `source` מפוענח אוטומטית בשלוש הצורות האלה:

| מה שנשלח                       | איך זה נוחת                                |
| ------------------------------ | ------------------------------------------ |
| `"ULTIMATE – YES"`             | חבילה `ULTIMATE`, ספק `יס`                 |
| `"פלאפון – 500GB 5G Together"` | ספק `פלאפון`, חבילה `500GB 5G Together`    |
| `"טריפל – יס"`                 | קטגוריה `טריפל`, ספק `יס`                  |
| `"טריפל"`                      | קטגוריה `טריפל`                            |
| `"קמפיין - אביב"`              | נשאר כמות שהוא בעמודת "מקור"               |

**סדר החלקים לא משנה** — מה שמזוהה כספק מוכר הוא הספק, מה שמזוהה כשם
קטגוריה הוא הקטגוריה, ומה שנשאר הוא החבילה. אם שני החלקים מזוהים כספק,
או אף אחד מהם, הערך נשאר כמות שהוא ולא מומצא ממנו כלום.

כששדה מפוענח כך, הוא לא נכפל גם ל"מקור" — שם נרשם שם השותף.

עדיף לשלוח `category`, `packageName` ו-`providerName` בנפרד; הפענוח הוא
רשת ביטחון, לא החוזה.

### שיוך

**הליד נכנס ללא שיוך.** הוא נוחת במאגר וגלוי להנהלה בלבד, עד שמנהל משייך
אותו לעובד — עובד רואה אך ורק לידים שמשויכים אליו.

- `LEADS_API_AUTO_ASSIGN="on"` מפעיל חלוקה אוטומטית: הליד הולך לנציג הפעיל
  (`role=agent` או `employee`) עם **הכי מעט לידים פתוחים**. מנהלים ובעלים
  לא בתור. שוויון נשבר לפי סדר א״ב, כך שהתוצאה דטרמיניסטית.
- בלי אף נציג פעיל הליד נשאר ללא שיוך בכל מקרה.

## תשובות

| קוד   | גוף                                            | מתי                                    |
| ----- | ---------------------------------------------- | -------------------------------------- |
| `201` | `{"success":true,"id":"..."}`                   | הליד נוצר                              |
| `200` | `{"success":true,"duplicate":true,"id":"..."}` | הטלפון כבר קיים — לא נוצר ליד כפול     |
| `400` | `{"success":false,"error":"..."}`               | שדה חובה חסר או ערך לא תקין            |
| `401` | `{"success":false,"error":"..."}`               | מפתח חסר או לא מוכר                    |
| `413` | `{"success":false,"error":"..."}`               | גוף הבקשה גדול מ-16KB                  |
| `429` | `{"success":false,"error":"..."}`               | יותר מ-120 בקשות בדקה מאותו מפתח       |
| `503` | `{"success":false,"error":"..."}`               | אין משתמשים במערכת לשייך אליהם את הליד |

## בדיקת חיים

```
GET https://<host>/api/leads     (עם אותה כותרת x-api-key)
```

מחזיר `{"success":true,"partner":"<שם השותף>"}` — דרך לוודא שהמפתח עובד בלי
ליצור ליד.

## דוגמה

```bash
curl -X POST https://<host>/api/leads \
  -H "Content-Type: application/json" \
  -H "x-api-key: <המפתח>" \
  -d '{"fullName":"ישראל ישראלי","phone":"0501234567","category":"cellular","source":"דף נחיתה"}'
```

## הערות מימוש

- **שרת-אל-שרת בלבד.** אין כותרות CORS בכוונה: קריאה מדפדפן הייתה מחייבת
  להטמיע את המפתח ב-JavaScript של הדף, כלומר לפרסם אותו. שותף שרוצה טופס
  בדפדפן צריך לתווך אותו דרך השרת שלו.
- **דדופ לפי טלפון.** אותו כלל כמו בייבוא CSV. שותף שמנסה שוב אחרי timeout
  מקבל `200` עם `duplicate: true` ולא יוצר ליד שני.
- **גבול הדדופ:** הבדיקה היא "לחפש ואז ליצור" בלי נעילה, ולכן **שתי בקשות
  עם אותו טלפון באותן מילישניות** יכולות שתיהן ליצור ליד. נמדד בפועל: פער
  של 29ms חמק. ניסיון חוזר אמיתי (שניות אחרי) נתפס כרגיל. אין כאן אילוץ
  `unique` על העמודה כי במערכת יש טלפונים כפולים לגיטימיים (בני משפחה,
  ייבוא CSV). אם יתגלו כפילויות אמיתיות — הפתרון הוא
  `pg_advisory_xact_lock` על ה-hash של הטלפון סביב הבדיקה והיצירה.
- **הנתיב פתוח בשער הגישה** (`ACCESS_KEY` ב-`src/proxy.ts`) — לשרתי השותפים
  אין עוגייה. הוא מאמת את עצמו דרך `x-api-key` ולא נשען על שום שכבה מעליו.
- **ביטול מפתח שדלף:** מסירים אותו מ-`LEADS_API_KEYS` ומפעילים מחדש. אין
  מיגרציה ואין פריסת קוד.
- **הגבלת קצב:** 120 בקשות לדקה למפתח. המונה חי בזיכרון התהליך, כלומר
  בפריסה serverless התקרה האפקטיבית גבוהה יותר — המטרה היא לעצור שותף עם
  באג בלולאה, לא להיות מכסה מדויקת.
- **מסך הלידים מתרענן לבד** כל דקה ומציג טוסט כשנכנסים לידים חדשים
  (`AUTO_REFRESH_MS` ב-`LeadsClient.tsx`).

## משתני סביבה שחייבים להיות בייצור

| משתנה             | למה                                                            |
| ----------------- | -------------------------------------------------------------- |
| `LEADS_API_KEYS`  | בלעדיו כל בקשה נדחית ב-401                                     |
| `ACCESS_KEY`      | בלעדיו כל מי שמגיע לכתובת רואה את המערכת. לא חוסם את `/api`     |
| `DATABASE_URL`    | ה-pooler של Supabase                                            |
| `DATA_SOURCE`     | חייב להיות `prisma`, אחרת הלידים נשמרים בזיכרון ונמחקים        |

`ACCESS_KEY` **לא** משפיע על `/api/leads` — הנתיב פתוח בשער בכוונה, ומאמת
את עצמו דרך `x-api-key`. אפשר להפעיל את שניהם יחד.
